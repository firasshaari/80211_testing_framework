Reading the Allure report

Every run keeps a full Allure report, linked from its summary page. Allure is a static site and must be served — the console serves it for you, so the link just works.

Where to look, in order

  1. Categories — always first. It buckets failures by cause, not by test, so one defect hitting twenty cases collapses into one row. The run summary page in this console shows the same grouping without needing Allure at all.
  2. Overview — the totals, plus the trend across runs.
  3. Behaviors — epic → feature → story, which here is OpenWiFi regression → feature area → example group. The view for "how is security doing", rather than "which test failed".
  4. Suites — the raw pytest hierarchy, for when you already know the example name.
  5. Graphs — the duration histogram is the practical one: a case that normally takes 40 s and took 200 s was retrying something.
  6. Timeline — wall-clock order. This is where bench faults show themselves, as a cliff where every later case starts failing at the same stage.

Anatomy of a case

Title "… · 2G"The example's summary plus the band this cell pinned. The same example appears once per band.
DescriptionExample name, area, group, forwarding mode and the physical requirements it declares. If it skipped, the unmet requirement is named here.
"N SSID(s) come up"Carries two attachments. "visible in a station scan" is the honest one — it lists each SSID with yes or NO from the station's own scan, which is the only way to tell "the AP says the BSS is up" apart from "a beacon actually reached the air".
"Client joins and passes traffic"One nested step per SSID, labelled name (proto). The per-SSID checks appear as further steps inside it.
"… behaves as configured"The AP-side checks. Present only if at least one SSID joined — there is no point asking whether a feature works when nothing reached it.
"scope of this check"An honesty note, attached when a check deliberately proves less than its name suggests. Telemetry collection is verified; delivery to the controller is not observable with the agent disabled.

Reading the failure message

Failed: 5 of 6 SSID(s) worked end to end; 1 did not
  ap-psk (psk): Did not associate to 'ap-psk'
                within 45s (last wpa_state=SCANNING)

Three things to read off it. The ratio — 5 of 6 means the radio, band plan and data path are fine and one SSID is the problem, which is a very different bug from 0 of 6. The proto in brackets names which security mode broke. The terminal wpa_state: SCANNING means the client never found something it could negotiate with; 4WAY_HANDSHAKE means it found it and the key exchange failed; ASSOCIATED that stalls means 802.1X never completed.

What "skipped" means here

Skips are not gaps in the suite — they are the capability layer refusing to report a meaningless result. A case skips when the bench physically lacks what the example needs: a 6 GHz radio, a Wi-Fi 7 client, a second AP, a managed switch, a GPS or WWAN module, an external DHCP or captive backend. A skip is a statement about the bench, never about the AP.
