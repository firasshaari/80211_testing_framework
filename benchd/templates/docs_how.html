How a run works

The console never reimplements a test. It spawns the same pytest command a person would type, against a config it wrote for this run. Every stage below is an allure.step, so the report shows exactly how far a case travelled before it stopped.

The guards that stop a test bricking the bench

  • SSH is forced onto the WAN. Most upstream examples list ssh only on the downstream LAN; applying one unmodified tears down management access.
  • A rollback is armed before each apply and cancelled only once management access is proven, so a config that cuts the AP off recovers by itself.
  • The apply runs detached, so a dropped SSH session does not kill the render.
  • The uCentral agent is held down for the apply window — it otherwise restarts itself and races the renderer.

Why the station is the source of truth

Reading a setting back off the AP only proves it was written down. Wherever the difference is observable, a check prefers evidence from the client: what it negotiated, which address it got, which access category a marked frame arrived in. That is also why throughput is measured against a wired peer the station raises for itself inside a network namespace — both ends are the same host, but the namespace has no route to the wireless address, so the kernel cannot short-circuit the transfer and the traffic must cross the air.

Preflight

Before any sweep the console checks the station is reachable, its radio is present and can scan, RADIUS is running and the AP answers. A failure blocks the run. This exists because three long sweeps were lost to conditions that take seconds to detect, and each produced a full run of failures that looked like AP defects and were not.
